# MPS Plugins: Declaration vs Packaging

Two separate nodes are involved. `BuildMps_IdeaPlugin` (a *part*, editor keyword `idea plugin`) **declares** a plugin for the IntelliJ platform that MPS and MPS-based standalone IDEs run on — the artifact users install into MPS. `BuildMpsLayout_Plugin` (a *layout entry*, keyword `plugin`) **packages it into the output**. The `Idea` in the concept name refers to that platform; the output is always installed into MPS or into an MPS-based IDE.

## `BuildMps_IdeaPlugin` (in `parts`)

```json
{
  "concept": "jetbrains.mps.build.mps.structure.BuildMps_IdeaPlugin",
  "properties": [{ "name": "id", "value": "com.example.MyPlugin" }],
  "children": [
    { "role": "name",    "nodes": [ /* BuildStringNotEmpty: display name */ ] },
    { "role": "version", "nodes": [ /* BuildStringNotEmpty: "1.0" */ ] },
    { "role": "containerName", "nodes": [ /* BuildStringNotEmpty: folder name inside zip */ ] },
    { "role": "content", "nodes": [{
        "concept": "jetbrains.mps.build.mps.structure.BuildMps_IdeaPluginGroup",
        "references": [{ "role": "group", "target": "MyPlugin" }]
    }]},
    { "role": "dependencies", "nodes": [{
        "concept": "jetbrains.mps.build.mps.structure.BuildMps_IdeaPluginDependency",
        "references": [{ "role": "target", "target": "r:874d959d-e3b4-4d04-b931-ca849af130dd(jetbrains.mps.ide.build)/4973949960459588488" }]
    }]}
  ]
}
```

### Key Properties / Children

| Role | Purpose |
|---|---|
| `id` (property) | The plugin id written after the `idea plugin` keyword; becomes `<id>` in the generated `plugin.xml`. **Unique.** |
| `name` | Human-readable display name |
| `version` | Plugin version string |
| `containerName` | Folder name inside the zip (often same as `id`) |
| `description`, `vendor` (`BuildMps_IdeaPluginVendor`: `name`, `url`) | Optional `plugin.xml` metadata |
| `content` | `BuildMps_IdeaPluginGroup` (reference `group` → a `BuildMps_Group`) or `BuildMps_IdeaPluginModule` (reference `target` → a single module) |
| `dependencies` | `BuildMps_IdeaPluginDependency` (reference `target` → another `BuildMps_IdeaPlugin`, local or from a dependency script) |
| `pluginXml`, `pluginXmlProvided` (property), `xml` | Choose the `plugin.xml` strategy and hold extra XML, see below |

Every plugin that contains languages needs the MPS core plugin (`jetbrains.mps.core`, which provides `BaseConcept` and `INamedConcept`) among its dependencies (node `…/4973949960459588488`, declared in the `mpsCore` script of `jetbrains.mps.ide.build`; used by `samples/sampleJavaExtensions`). Many scripts in this repo (for example `SampleCustomAspect.build` and MPS's own plugin scripts) depend on `com.intellij.modules.mps` instead (node `…/4973949960459706697`, declared in `mpsWorkbench`); it is an equally valid choice. Both resolve through the `mps` dependency script.

If a module in plugin A depends on a module in plugin B, plugin A **must** list B as a `BuildMps_IdeaPluginDependency` — the build-language type system reports the violation.

## `plugin.xml` Strategies

The docs name three ways to get a `plugin.xml`: build it from the script alone, enrich a provided file, or use a custom file only. In the editor you choose with the intention/menu on the descriptor line of the `idea plugin` node:

| Menu option | Node state | Effect |
|---|---|---|
| "from generated by default plugin.xml file" (default) | `pluginXml` empty, `pluginXmlProvided = false` | MPS synthesizes `plugin.xml` from `id`, `name`, `description`, `version`, `vendor`, `dependencies` and the module registration. Extra elements (extensions, extension points) go into the `xml` role as `jetbrains.mps.core.xml` nodes, so that language must be a used language of the build model. |
| "from custom plugin.xml file" | `pluginXml` = path (`BuildSourcePath`) to your file, `pluginXmlProvided = false` | The generator takes that file as the descriptor. The `xml` list is hidden. |
| "from provided plugin.xml file" | `pluginXml` empty, `pluginXmlProvided = true` | No descriptor is generated; your layout must supply `META-INF/plugin.xml` itself. |

`name`, `version`, `content` and `dependencies` stay visible in every mode; `content` still decides which modules are packaged.

The synthesized `plugin.xml` registers the packaged modules through the `com.intellij.mps.LanguageLibrary` extension point (`<mps.LanguageLibrary dir="/languages" />`). By default every module in an installed plugin is visible to users. To hide implementation modules from import dialogs (they still work), the `LanguageLibrary` element needs `hide="true"` and the plugin must declare a visibility pattern via the `com.intellij.mps.VisibleModuleMask` extension point. Both live in `plugin.xml`, so a plugin that hides modules typically uses the custom or provided descriptor.

## `BuildMpsLayout_Plugin` (in `layout`)

```json
{
  "concept": "jetbrains.mps.build.mps.structure.BuildMpsLayout_Plugin",
  "references": [{ "role": "plugin", "target": "MyPlugin" }],
  "children": [{
    "role": "packagingType",
    "nodes": [{
      "concept": "jetbrains.mps.build.mps.structure.BuildMpsLayout_AutoPluginLayoutType"
    }]
  }]
}
```

`BuildMpsLayout_PluginDescriptor` (keyword `plugin descriptor of`, reference `plugin`) places only the generated `plugin.xml`, for hand-built layouts.

## Packaging Types

| Concept | Behavior |
|---|---|
| `BuildMpsLayout_AutoPluginLayoutType` (`auto packaging`) | **Auto**: module jars go into the plugin's `languages/` folder; the generated `plugin.xml` is packed into a jar under the plugin's `lib/`. Use this unless you have a specific reason not to. |
| `BuildMpsLayout_ManualPluginLayoutType` (`manual packaging`) | **Manual**: you specify the plugin's nested layout of folders and jars yourself. More work, total control. |

Library jars that the plugin needs at runtime go into subfolders of the plugin folder (copied with `BuildLayout_File`); the platform adds them to the plugin classpath.

## Installing the Result

Running Ant produces a zip laid out per the `layout`. Install it through **Settings → Plugins → Install Plugin from Disk**, or unzip it into the plugins folder and restart:

- Windows / Linux: `USER_HOME/MPS_version/config/plugins` or `MPS_HOME/plugins`
- macOS: `~/Library/Application Support/MPS_version/` or `MPS_HOME/plugins`
