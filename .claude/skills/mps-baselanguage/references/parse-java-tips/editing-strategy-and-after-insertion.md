## Editing Strategy

* **New class / method**: use `mps_mcp_parse_java_and_insert` for rapid skeleton / body creation.
* **Targeted changes**: use node-by-node AST editing (e.g. `mps_mcp_update_node`) to preserve surrounding structure.
* **Delete-and-recreate**: use only for roots you just created in the current session that have no incoming references.

## After Insertion

* **Reference resolution**: after insertion, call `mps_mcp_print_node` `format: "AGENTIC VIEW"` to verify references resolved correctly (`!unresolved` marks a broken one).
* **Dependencies**: ensure the containing models and modules of all referenced nodes are imported. A METHOD/STATEMENTS insert has no `import` lines: a short class name resolves only if a single imported model declares it (`EditorComponent` is in both `jetbrains.mps.nodeEditor` and `jetbrains.mps.openapi.editor`), so write such names fully qualified.
* **`UnknownDotCall` on a static interface method** (`List.of`, `Path.of`): the parser leaves those unresolved, and `mps_mcp_check_root_node_problems` with `autoApplyQuickFixes` does not fix them; see `references/java-parser-capabilities/unsupported-and-workarounds.md` in the `mps-model-manipulation` skill root after loading that companion skill from the same origin.
* **Identity placeholders**: in model code, any `PersistenceFacade.getInstance().create{Model,Module,Node}Reference("…")`, `new SNodePointer(…)` or inline `MetaAdapterFactory` id the parser produced is a placeholder for an smodel literal (`model-ptr/`, `module-reference/`, `node-ptr/`, `concept/`, `link/`, `language/`). The exception is a constant field of a class that already keeps `LINKS`/`CONCEPTS` constants. Find each one in an `AGENTIC VIEW` print (`codeAsText: true`) and `SET` `CHILD` the literal over the whole call; neither `problems` nor `mps_mcp_check_root_node_problems` reports a leftover. Blueprints: `references/design-time-identities.md` in the `mps-model-manipulation` skill root after loading that companion skill from the same origin.
* **Type-system problems (`problems` response field)**: every success envelope (`ok:true`) carries a `problems` array. Each entry has `severity` (`error`/`warning`), `message`, and the offending node's `reference` and `concept`. It lists the problems found *within the inserted nodes' subtrees* using the same checkers as `mps_mcp_check_root_node_problems`. An **empty** array means the insert type-checks; a **non-empty** array means the insert succeeded (and, for normal project models, was persisted) but left problems you must fix (for example, a lambda whose closure type does not match the destination slot). `ok:true` does **not** by itself imply a clean model — always inspect `problems`.
