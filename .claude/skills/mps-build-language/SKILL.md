The **MPS Build Language** is a declarative DSL (a stack of MPS languages on top of Ant) that generates an Apache Ant `build.xml` file. It is used to package MPS language plugins (installed into MPS or an MPS-based IDE), build standalone IDE/RCP distributions, package plain Java modules, and run MPS tests or generation-diff tests. Build scripts are root nodes of concept `BuildProject` inside a regular **solution** module; pressing Make on that solution runs a generator that writes `build.xml` to disk.

## Critical Directives

- The generator writes `build.xml` — it does **not** invoke Ant. To produce artifacts you must run `ant` separately (from MPS right-click → Run, or from the command line in the generated folder).
- Build scripts are MPS nodes. Edit them via projectional editing or `mps_mcp_*` JSON tools. **Never hand-edit the `.mps` file** as if it were Ant XML.
- Declaring a module in `BuildProject.parts` **does not** cause it to be built. Only items **referenced from the `layout`** end up in the output. `parts` is declaration; `layout` is packaging.
- `ant build` **compiles and packages** the Java already in `source_gen` (with `useMakeTask`, it compiles nothing and packages `classes_gen`); it does **not regenerate** languages (`build` does not depend on `generate`). Make the languages in MPS first, or run `ant -f <fileName> generate build`. The `mps` build plugin's full-make task (`useMakeTask`) makes `generate` run `<mps.make>` (generate and compile in MPS) instead of `<generate>`, and skips the `javac` targets; `build` still skips `generate`. `generate` rewrites `source_gen`, which may be under version control.
- Always import `jetbrains.mps.ide.build` (`422c2909-59d6-41a9-b318-40e6256b250f`) on the build solution — it is the catalog of MPS's own build scripts (`mps`, `mpsStandalone`, plugin scripts such as `mpsMakePlugin`), the plugins they declare (`jetbrains.mps.core`, `com.intellij.modules.mps`), their modules (`JDK`, `MPS.Core`, …), and the `IDEA` external layout of the platform jars.
- After every change to a module's `.mpl` / `.msd`, re-run the **Reload Modules From Disk** intention (`jetbrains.mps.build.mps.intentions.ReloadModulesFromDisk_Intention`, Alt+Enter on any node of a `BuildProject` that declares modules; its target node is the `BuildProject`; the docs call it *Load required information from file*, which is also the quick fix offered on an out-of-sync module). When several interdependent modules are declared at once, **apply it again until the error count stops changing** — the first pass names the modules, the second wires their dependencies on each other ("… should be extracted into build script" errors). Build-script module dependencies must match the actual `.mpl` declarations or the chunk generator throws "class not found".
- A `BuildMps_Group` must contain the **transitive closure** of language dependencies. The editor marks missing members with red squiggles.
- Always set `internalBaseDirectory` — every relative path is resolved against it.
- **A clean root check does not prove the script generates.** Some errors appear only at MAKE time (for example a module's library jar missing from the layout, see `references/common-failures.md`); always MAKE the build model before running Ant.
- **Check macro and branding references after inserting.** A `BuildVarRefStringPart.macro` name target may or may not resolve, even for the script's own macros (in one test `build.number` and `date` resolved while `version` did not; same-named macros in dependency scripts can make a name ambiguous). The `name` of `BuildMps_Branding` is a read-only derived value (`<full name> <major>.<minor>`), so it cannot serve as a name target. After the insert, read `fixReferences.stillBroken`; when it is non-zero, print the root in AGENTIC VIEW, which marks broken references `!unresolved`. Also make sure no macro reference carries an `@mN` suffix (a target in another model). Set those references, and every branding reference, by `r:` node reference with `mps_mcp_update_node`. Name targets for groups, plugins and `mps_home` (`BuildSourceMacroRelativePath`) resolve fine.

## Common-Path Workflow

For a typical "package an MPS language as an installable plugin" task:

1. **Create the build solution.** In MPS the **Build Solution** wizard (launched from the Project View; choose the MPS plugin output) creates the solution, model and a pre-filled script; continue at step 5 to review it. Manually: a regular solution (not language) named `<project>.build`; in its `.msd`, add a dependency on `jetbrains.mps.ide.build` and declare languages `jetbrains.mps.build` and `jetbrains.mps.build.mps`. Its Java facet must be `compile="mps" classes="mps"`; `mps_mcp_create_module` sets this by default, so check it only for a solution created another way. See `references/solution-setup.md`.
2. **Create the model** (conventionally `<project>.build`) with the same languages as used languages.
3. **Insert the `BuildProject` root** with `name`, `internalBaseDirectory` and, optionally, `fileName` (empty means `build.xml`). Use `mps_mcp_insert_root_node_from_json` with the skeleton in `references/buildproject-skeleton.md`.
4. **Add plugins to `BuildProject.plugins`:** at minimum `BuildJavaPlugin` and `BuildMPSPlugin`. Add `BuildModuleTestsPlugin` / `BuildSolutionRunnerPlugin` only when needed (see `references/plugins-and-macros.md`).
5. **Declare macros** (`mps_home`, plus version/timestamp Var macros). An `mps_home` without `defaultPath` always draws the warning "mps_home macro should point to the unzipped generic MPS distribution"; give it a `defaultPath` to an MPS installation to keep the check clean (`-Dmps_home` still overrides it). See `references/plugins-and-macros.md`.
6. **Add the dependency** on the `mps` script (a `BuildProjectDependency`, artifacts at `$mps_home`) to `BuildProject.dependencies` — with the default Java compiler this is the only dependency a language plugin needs. See `references/dependencies.md`.
7. **Add parts:** one `BuildSource_JavaOptions` with `copyResources = true` (otherwise the concept icons MPS generates into `source_gen` are left out of the language jars) and an explicit `javaLevel`, then a `BuildMps_Language` or `_Solution` per MPS module (enter the descriptor path and, on a solution, `sourcesKind = sources` — empty builds the same but fails the MCP check — then run **Reload Modules From Disk**, twice when the modules depend on each other), wrapped in `BuildMps_Group`s. Leave each language's `generator` empty: Reload creates the `BuildMps_Generator` declaration. One created from a JSON blueprint gets an empty `path`, and with `useMakeTask` `ant … generate` then fails with `bad file`. Like the wizard, give each language a resources entry (`BuildMps_ModuleResources`, `icons/**, resources/**` from the module folder). Where the checker reports the info "Need resources entry" (on any language or solution whose module uses `jetbrains.mps.lang.resources`), apply its quick fix `jetbrains.mps.build.mps.typesystem.addModuleResources_QuickFix` with `mps_mcp_apply_intention` on that declaration. The fix is not auto-applicable, so `autoApplyQuickFixes` skips it, and it is not offered where the info is absent. Include the runtime solutions of your languages. Add a `BuildMps_IdeaPlugin` (`idea plugin`, the MPS plugin declaration) whose `content` references the groups and whose `dependencies` include the MPS core plugin. See `references/mps-modules.md` and `references/mps-plugins.md`.
8. **Define the layout:** one `BuildLayout` root, typically wrapping a `BuildLayout_Zip` named `<plugin>.zip`, with one `BuildMpsLayout_Plugin` (`AutoPluginLayoutType`) per plugin. Jars that a module's descriptor references (Reload adds them as `BuildMps_ModuleDependencyJar`) go into the plugin entry's `children`, e.g. `folder lib { file <jar> }`. See `references/layouts.md` and `references/mps-plugins.md`.
9. **Make the build solution** (Ctrl-F9 on the model) — this writes `build.xml` at `internalBaseDirectory/fileName`.
10. **Run Ant** from MPS (right-click `BuildProject` → Run) or from the base directory: `ant -f <fileName> build` (add `generate` before `build` to regenerate the modules with the target MPS), pointing the script at the MPS installation with `-Dmps_home=/path/to/MPS` or `-Dartifacts.mps=/path/to/MPS`. Run Ant on the JDK the target MPS runs on; its bundled JBR works. Artifacts land in `build/artifacts/<script name>/`.
11. **Verify the zip** — see the checklist in `references/mps-plugins.md`.
12. **Install** the zip through the plugin manager or by unzipping it into the MPS plugins folder — see `references/mps-plugins.md`.

For other task families: standalone IDE distributions → `references/standalone-ide.md` (without the wizard: `references/standalone-manual-recipe.md`); plain Java packaging → `references/java-parts.md`; tests → `references/tests-and-workflow.md`.

## Disambiguation — Don't Conflate These

Four "dependency" concepts and two "aspect" concepts are routinely confused. See `references/disambiguation.md` for the full table before designing dependencies or parts. Quick rule:

- Solution `.msd` deps = what the build solution itself needs at edit time (just `jetbrains.mps.ide.build`).
- `BuildProject.dependencies` = references to other build scripts (`BuildProjectDependency` → `mps`, `mpsStandalone`, siblings) or external layouts (`BuildExternalLayoutDependency` → `IDEA`).
- `BuildSource_JavaModule.dependencies` = classpath of a plain Java module.
- `BuildMps_*.dependencies` = mirror of the actual `.mpl` / `.msd`, auto-filled by **Reload Modules From Disk**.
