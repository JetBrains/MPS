# Creating a new empty MPS project

There is **no MCP tool to create a new MPS project from scratch**. All MPS MCP tools require an already-open project matching `projectPath`. To create a new project headlessly, write the minimal project descriptor files directly on disk, then open the project in MPS using the CLI activation protocol.

## Minimal file structure

MPS directory-based projects store project configuration in a `.mps/` subdirectory under the project root:

```text
<project-root>/
└── .mps/
    ├── modules.xml          # Core MPS project descriptor (required)
    ├── .gitignore           # Ignores workspace state and shelves (recommended)
    └── migration.xml        # Migration baseline + executed flags (required)
```

## File templates

### 1. `.mps/modules.xml` (Required)

Defines the `MPSProject` component (`StandaloneMPSProject`). Holds module registrations. For an empty project:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project version="4">
  <component name="MPSProject">
    <projectModules />
  </component>
</project>
```

When modules (solutions, languages, generators) are added later (e.g. via `mps_mcp_create_module`), MPS automatically populates `<projectModules>` with `<modulePath>` entries.

### 2. `.mps/.gitignore` (Recommended)

Excludes user-specific workspace state and shelves from version control:

```gitignore
# Default ignored files
/shelf/
/workspace.xml
```

> **Note on `workspace.xml`:** MPS automatically creates and maintains `.mps/workspace.xml` to store local IDE state (tool windows, open editors, task history, color schemes). It should **never** be authored manually or committed to version control.

### 3. `.mps/migration.xml` (Required)

Without it MPS treats the directory as a project that predates 2021.1 (`project.baseline.version` defaults to **211**), selects every project migration introduced since, and opens the **modal** Migration Assistant the first time the project is opened — blocking every `mps_mcp_*` call until a human dismisses it. The content is specific to the MPS release that opens the project.

**MPS 2026.2 — use this file as is:**

<!-- new-project-migration-xml: generated by scripts/new_project_migration_xml.py; MigrationXmlExampleTest fails when it drifts -->

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project version="4">
  <component name="MigrationProperties">
    <entry key="project.baseline.version" value="262" />
  </component>
</project>
```

That is the complete file for a 2026.2.x MPS: platform baseline `262` and nothing else, because 2026.2 introduced no project migration at that baseline (a real New Project would mark such a migration executed rather than run it; every older one is already covered by the baseline). Verified against branch head `262.9437`.

Confirm it applies to the MPS you are about to launch — it must print `262` and `v_2026_1` (the newest package is 2026.1's, which the baseline already covers):

```bash
MPS="/path/to/mps-home"                                         # install dir, macOS .app, or source checkout
R="$MPS"; [ -d "$MPS/Contents" ] && R="$MPS/Contents"           # macOS .app bundle
B="$R/build.txt"; [ -f "$B" ] || B="$R/Resources/build.txt"
awk 'NR==1 { sub(/^[^0-9]*/, ""); sub(/[^0-9].*/, ""); print }' "$B"    # platform baseline
M="$R/plugins/mps-project-migrations"
{ find "$M/languages" -name '*.jar' -exec unzip -l {} \; 2>/dev/null   # not a glob: zsh aborts on no match
  ls "$M/solution/source_gen/jetbrains/mps/ide/mpsmigration" 2>/dev/null; } |
  grep -o 'v_2[0-9_]*' | sort -u | tail -1                      # newest migration package
```

**Anything else** — a different baseline, a newer migration package, or a 2026.2.x bugfix that added one — means the file above is incomplete and the Migration Assistant will appear. Derive the right one instead: `references/derive-migration-xml.md` generates it from any MPS installation, offline. Same for a build you cannot check.

## Step-by-step creation workflow

### Step 1: Create directories and descriptor files

`modules.xml` and `.gitignore` are static text: write them with whatever file tool you have — the shell snippets below are only a convenience. Write UTF-8 **without a BOM**, which is what MPS itself writes.

macOS / Linux:

```bash
PROJECT_DIR="/path/to/new/project"
MPS_HOME="/Applications/MPS 2026.2.app"     # the MPS that will open it (install dir, .app, or checkout)
mkdir -p "$PROJECT_DIR/.mps"

# 1. modules.xml
cat <<'EOF' > "$PROJECT_DIR/.mps/modules.xml"
<?xml version="1.0" encoding="UTF-8"?>
<project version="4">
  <component name="MPSProject">
    <projectModules />
  </component>
</project>
EOF

# 2. .gitignore
cat <<'EOF' > "$PROJECT_DIR/.mps/.gitignore"
# Default ignored files
/shelf/
/workspace.xml
EOF

# 3. migration.xml — required (missing file ⇒ baseline 211 ⇒ modal Migration Assistant).
# For a 2026.2 MPS, write the file printed in section 3 verbatim. For any other release
# generate it — never hardcode another release's ids (references/derive-migration-xml.md):
python3 scripts/new_project_migration_xml.py "$MPS_HOME" "$PROJECT_DIR"   # from the skill directory
```

Windows (PowerShell). `Set-Content -Encoding UTF8` adds a BOM in Windows PowerShell 5.1, so write through `[IO.File]`, which emits none — and give it absolute paths, because it resolves relative ones against .NET's current directory, not PowerShell's:

```powershell
$project = "C:\work\new-project"
New-Item -ItemType Directory -Force -Path "$project\.mps" | Out-Null

# 1. modules.xml
[IO.File]::WriteAllText("$project\.mps\modules.xml", @'
<?xml version="1.0" encoding="UTF-8"?>
<project version="4">
  <component name="MPSProject">
    <projectModules />
  </component>
</project>
'@)

# 2. .gitignore
[IO.File]::WriteAllText("$project\.mps\.gitignore", @'
# Default ignored files
/shelf/
/workspace.xml
'@)

# 3. migration.xml — generated, never hardcoded (section 3)
py -3 scripts\new_project_migration_xml.py "C:\Program Files\JetBrains\MPS 2025.3" $project
```

### Step 2: Open the project in MPS

Open the newly created directory in MPS using the CLI activation protocol:

1. Follow `open-via-cli.md` and the appropriate OS guide (`examples-macos.md`, `examples-linux.md`, or `examples-windows.md`).
2. Run the activation script passing `PROJECT_DIR`.
3. *Note on open projects*: If another project is currently open, opening a new project may cause MPS to show the "Open Project: New Window / This Window" prompt. If MPS is already at the Welcome screen (no projects open), it opens immediately without prompting. You can close existing projects beforehand using `mps_mcp_close_project`.

### Step 3: Verify with MCP

Verify that the project was opened successfully:

```bash
mps_mcp_list_open_projects(projectPath=PROJECT_DIR)
```

The response should list the project with `hasMpsProject: true`. Subsequent `mps_mcp_*` calls can now target this project.

### Step 4: Populate the project

Once open and verified, use standard MCP tools to configure and populate the project:
- `mps_mcp_initialize_project_for_agents` — installs agent skills and guides if the project will be used with AI agents.
- `mps_mcp_create_module` — creates solutions, languages, devkits, or generators within the project.

## What not to do

- Do not author `.mps/workspace.xml` manually; let MPS create it on first open.
- Do not create old-style file-based (`.mpr`) projects; directory-based `.mps` is the standard for modern MPS.
- Do not attempt to call MPS MCP tools (such as `mps_mcp_create_module`) before the project is opened in MPS.
- Do not reuse a `migration.xml` written for a different MPS release, and do not invent migration ids: either the MPS is a 2026.2 build and the file in section 3 applies verbatim, or derive one with `references/derive-migration-xml.md`.
