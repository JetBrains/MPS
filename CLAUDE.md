# Agents Guide for This Project

This project is a mixed JetBrains MPS + plain Java/Kotlin codebase. Developers use two environments against the same checkout:
- IntelliJ IDEA for editing, debugging, testing, and inspecting Java/Kotlin code, including code generated by MPS.
- JetBrains MPS for editing languages, models, generators, and other MPS artifacts.

Use IDEA tools for JVM work and the full MPS MCP toolset for model work. Use this file as the cross-environment entry point.

For any MPS work, load the `mps-mcp-workflow` skill; it holds the MPS critical directives, project resolution, validation, and the index of companion skills. If your agent runtime does not explicitly confirm that project skills are auto-loaded, read `.agents/skills/mps-mcp-workflow/SKILL.md` before changing MPS artifacts.

## ⚠️ WARNING: Never Read Raw MPS Model Files

Do not open, parse, or edit `.mps`, `.mpl`, or other MPS XML files as text: the serialized format is opaque, gives no semantic insight, and hand-edits corrupt models. Use the MPS MCP tools (`mps_mcp_*`) instead. If the MPS MCP server is not connected, ask the user to start MPS and enable it; a connected server whose tools were filtered or deferred is not this case — restore the full toolset as described below.

## ⚠️ Keep the Full MPS MCP Toolset

The `mps_mcp_*` tools are how MPS code is read and edited, not an optional add-on the way MCP tools are for plain-text code. Which of them a session will need cannot be guessed from the opening request — inspection, validation, generation, and editing tools get pulled in as the work unfolds — so a relevance filter that keeps only an opening subset will strand the session.

- Do not reduce, defer, hide, or capability-filter the MPS MCP catalog. Keep every `mps_mcp_*` tool available for the whole session, including tools that do not look relevant yet. Pruning unrelated servers (IDEA, YouTrack, and the like) is fine; this rule is only about the MPS MCP server.
- If the host has already filtered that server (Junie: `[partially available]`, `[installed, but unavailable]`, or listed under servers that can be enabled), restore the entire server before any MPS work. In Junie, call `enable_mcp` on the MPS MCP server — the one that exposes `mps_mcp_*`, or, if it was fully filtered, the server named like `mps-mcp` rather than the IDEA or YouTrack server. If that call is not available, ask the user to enable the full server. Do not guess among unrelated servers.
- A filtered tool is not unavailable. Do not continue on a reduced subset, and do not fall back to file tools or raw `.mps` XML in its place. Only when the server is not connected at all, ask the user to start MPS and enable it.

## Project Nature: JVM + MPS

The repository has two kinds of source of truth: plain Java/Kotlin and related project files, edited and validated through IntelliJ IDEA tooling; and MPS models and language definitions, edited and validated through MPS MCP tools. Prefer the highest-level source of truth: if behavior is defined by an MPS language, model, or generator, fix the MPS artifact rather than only patching generated Java.

## Choose Tools By Task

- IDEA MCP tools: `.java`, `.kt`, `.kts`, XML, Ant, module, project, and run configuration files; inspections, symbol lookup, refactoring, builds, tests, debugging, and how hand-written code consumes generated code.
- MPS MCP tools: `.mps` models and every language aspect (structure, editor, constraints, typesystem, behavior, generator); model navigation, node editing, validation, and generation issues rooted in MPS artifacts.
- Plain file tools (Read, Grep, Glob, Bash) are fine for reading generated output, non-MPS configuration, and plain-text docs — never for editing `.mps` files.
- For cross-cutting tasks, inspect both sides before editing and validate both the MPS model and the affected JVM code path.

If a task requires model-aware editing and the MPS MCP server is not connected (a filtered or deferred toolset is not this case — restore it first), restrict changes to plain JVM, build, docs, and configuration files, explain the limitation, and ask whether to proceed with a workaround or wait for MPS-aware tooling.

## Rules For Java/Kotlin Work

- Prefer targeted validation first: inspect the affected file, build the affected module, run the smallest relevant test or run configuration.
- Follow existing module and test structure rather than introducing new build or test conventions.

Typical JVM-side areas: `core/`, `editor/`, `workbench/`, `platform/`, `plugins/`, `startup/`, `testbench/`, `jps/`, `IdeaPlugin/`.

## Project Resolution

One checkout can expose several projects to the same MCP server — this repository plus the IntelliJ platform sources opened alongside it (see Platform sources below). Pass the intended project's path on **every** call, starting with the first one: the absolute `projectPath` for IDEA tools, the MPS project's base directory as `projectPath` for MPS tools. The path must be at or inside the project that owns the code, never a parent directory. If you do not know it yet, pass the session's current working directory; if that is rejected, take the path from the rejection message, which lists the open projects, and reuse it for the session. When it is not obvious which open project a query or change targets, ask the user rather than guessing — open projects share one module repository, so the wrong choice silently returns the wrong nodes or gets a cross-project write refused.

## Rules For Generated Code

`source_gen/` and `classes_gen/` are recreated on every Make/Rebuild. Read them for inspection and debugging, but do not edit them when the source of truth is an MPS model or generator — unless the user explicitly asks, the directory is checked-in maintained source, or the edit is a temporary diagnostic step that you call out as such. Before editing generated code, identify where it comes from, whether generation will overwrite it, and whether the fix belongs in the generator, the model, or hand-written JVM code.

## Validation Expectations

Match validation to the kind of change, and prefer focused validation before broad suites. [`.agents/quality-gates.md`](.agents/quality-gates.md) is the single source of truth: it covers the JDK, build and test commands, run-configuration timeouts and monitoring, starting MPS from source, and the MPS-side checks.

## Skills

A skill is a set of local instructions stored in a `SKILL.md` file under `.claude/skills/<skill-name>/` (or `.agents/skills/<skill-name>/` for MPS-specific skills). Start with `mps-mcp-workflow` for the overview and a directory of every other skill. The `mps-*` skills here are hand-propagated copies of their blueprints in `plugins/mcp-tools/resources/jetbrains/mps/agents/mcp/skills/`, which is the source of truth: never run `mps_mcp_initialize_project_for_agents` here, and never delete these copies to let it run — edit the blueprint and re-propagate, by copying each changed skill folder over both catalogs. `SkillCatalogReplicationTest` in the mcp-tools test suite fails when the three trees differ.

In other checkouts, the installed guide (`plugins/mcp-tools/resources/jetbrains/mps/agents/mcp/templates/AGENTS_template.md`) states how to compare the `MPS_MCP_SKILL_VERSION.txt` stamps with `mpsBuild` from `mps_mcp_list_open_projects`. **This checkout is exempt:** the catalogs are hand-propagated blueprints and can be newer than the running plugin, so a missing `MPS_MCP_SKILL_VERSION.txt` is expected. Do not treat that absence as staleness, do not run the initializer, and do not delete the copies. `SkillCatalogReplicationTest` remains the freshness check.
