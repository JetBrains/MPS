# Common Failures and Pitfalls

- **Wrong stereotype.** A model without the `tests` stereotype will compile but its roots won't be discovered as JUnit tests.
- **Missing `jetbrains.mps.baseLanguage.unitTest`.** Without it, `NodesTestMethod` and assertion concepts are unavailable.
- **Solution missing the `tests` facet.** The test root must live in a Solution that carries the `tests` facet — Languages and Generators don't compile the test classes. Verify with `mps_mcp_get_project_structure(startingPoint="…")` (its `data.facets` array should include `"tests"` and `data.loadExtensions` should be `"NotAvailable"`). Attach at creation via `mps_mcp_create_module(…, facets="[\"tests\"]")`, or to an existing Solution via `mps_mcp_update_module_facet(facetType="tests", enabled=true)`.
- **Snippet relies on missing imports.** A `TestNode` snippet behaves like a tiny model — add the same `<use>` languages and `<import>` model references that the snippet would need standalone, or it will fail to resolve.
- **Out-of-process vs in-process.** Editor tests typically run in-process; setting "execute in same process = false" for an `EditorTestCase` works but tends to be slower and can mask classloader bugs. Use whatever the existing test module uses.
- **Migration test `outputNodes` regenerated from broken script.** "Generate Output from Input" *bakes in current behaviour*. If the script is wrong, the test will encode that. Diff before accepting.
- **Caret and selection in EditorTestCase.** Structure is compared before the selection, so a `CellReference` failure means the tree already matched: fix the `result` annotation, not the `code` block (the `before` row below is a tree diff, not a `CellReference` failure). What each annotation property does is in `editor-test-case.md` ("`AnonymousCellAnnotation`: what is set and what is compared").

  | Symptom | Cause | Fix |
  |---|---|---|
  | `expected:<0> but was:<N>` at `CellReference.java:61` or `:62` | the `result` annotation sets only `isLastPosition` / `caretPosition`, which are not compared; `selectionStart` / `selectionEnd` stay 0 | set both to the `was:` value from the message |
  | tree diff: typed text appears at the start of the cell, or the character Backspace / Delete should remove is still there | in `before`, a caret ≠ 0 with the default 0..0 selection counts as a text selection: typing inserts at `selectionStart`, and Backspace / Delete deletes the empty selection | in `before`, set `selectionStart` = `selectionEnd` = the caret offset |
  | `expected same:<…> was not:<…>` at `CellReference.java:57` | after the action, the selected cell belongs to another node (e.g. a child created by substitution) | put the `result` annotation on that node |
  | `ComparisonFailure` on the cell ids at `CellReference.java:58` (`expected:<…> but was:<…>`, the differing part in `[ ]`) | the action moved the caret to another cell | set the `result` `cellId` to the cell after the action; grep `setCellId(` in the generated `<Concept>_EditorBuilder_a.java` |
  | `expected null, but was:<…>` at `CellReference.java:64` / `:65`, or an assertion in the range branch (`:68-71`) | singular vs node-range selection mismatch | set `nodeRangeSelectionStart` / `End` only when the action leaves a node-range selection, pointing at `result` nodes |
  | `IllegalStateException: Cannot find cell reference in the test case 'before'` | no `AnonymousCellAnnotation` in `before` | add one |
  | the test passes although the caret is wrong | no `AnonymousCellAnnotation` in `result`, so the selection is not checked | add one |

  For an empty list role, target `empty_<role>`, *not* `refNodeList_<role>`.
- **`press VK_ENTER` is not the same as `invoke action Insert`.** Raw key dispatch via `PressKeyStatement` may bypass the action infrastructure that actually creates new children in a collection. When testing what Enter "does" in a cell, invoke the named action (`Insert`, `Delete`, `MoveUp`, `MoveDown` from `jetbrains.mps.ide.editor.actions`, etc.) rather than the keystroke.
- **Labels collide with names.** `node<label>` references look like identifiers but bind to the label, not a Java variable — pick distinct label names per test method.
- **`NodesTestMethod` is abstract.** The role `testMethods` declares `NodesTestMethod` as its child type, but that concept is abstract — use the concrete subtype `SimpleNodeTest`. Validation reports `"Abstract concept instance detected. Use one of sub-concepts instead."` if you instantiate the abstract type directly.
- **`TestNodeAnnotation` labels don't drive in-snippet reference resolution.** Labels are only resolvable through `TestNodeReference` inside test-method bodies. When the JSON insert needs to set a reference *inside the snippet* (e.g. `RoutineCall.routine`), use the target node's `name` (resolved via the language's own scope) or a persistent `r:` node ref — not the annotation label name.
- **`mps_mcp_update_node` mints a new persistent ref for the replacement.** The old ref is invalidated by the call, and the tool's response returns the *parent's* ref, not the new child's. If you need to act on the replacement again (e.g. add children to it), re-print the parent via `mps_mcp_print_node` and harvest the new child's ref from there.
- **`ScopesExpectedNode.ref` is not scope-resolved.** Auto-resolution of plain names works only where MPS has a scope for the reference (e.g. `RoutineCall.routine` which uses Kaja's scope). `ScopesExpectedNode.ref` targets `BaseConcept` generically — supply a persistent `r:` node ref. The stage-construction recipe in `references/scopes-test.md` covers this.
