## Deletion and completion tests

- **Deletion depends on a user setting.** Two-step deletion is on by default (`EditorSettings.useTwoStepDeletion`): a `Delete` / `Backspace` that starts from a caret may only mark the node for deletion, and only the next one deletes it. A selection that exactly covers the node's cell deletes at once. Fix the setting for the test by wrapping the action: `EditorTestUtil.runWithTwoStepDeletion({ => invoke action -> Backspace }, false);` (`true` tests the two-step behaviour). It needs the model `jetbrains.mps.lang.test.runtime` imported and the language `jetbrains.mps.baseLanguage.closures`. Parsing `EditorTestUtil.runWithTwoStepDeletion(() -> { int placeholder = 0; }, false);` gives a closure whose body holds one `BlockStatement`; replace that with the `InvokeActionStatement`. The make then warns "Closure generic throws types count doesn't match", which is harmless.
- **Completion:** `invoke action -> Complete` opens the menu, `type "..."` filters it, and `press ENTER` applies the selected item (no action applies a menu item). Blueprint: `{"concept": "jetbrains.mps.lang.test.structure.PressKeyStatement", "children": [{"role": "keyStrokes", "nodes": [{"concept": "jetbrains.mps.lang.plugin.structure.KeyMapKeystroke", "properties": [{"name": "keycode", "value": "VK_ENTER"}, {"name": "change", "value": "replace_all"}]}]}]}`. Recipe: put the caret where the pattern should start (the menu filters by the cell text left of the caret: `references/landscape.md` in the `mps-aspect-editor-menus-and-keymaps` skill root after loading that companion skill from the same origin), `invoke action -> Complete`, then assert `editor component.getNodeSubstituteChooser().isVisible()` (and, to check the offered items, `getNumberOfActions()`, or their texts: `ec.getSelectedCell().getSubstituteInfo().getMatchingActions("", false)` → `getMatchingText("")`, and `getDescriptionText("")` for the right-hand description, under a read action; `getMatchingActions(p, false)` filters by `canSubstitute`, not by matching text, so to assert what the popup shows keep only the items whose `getMatchingText(p).startsWith(p)`), then `type`, then `press ENTER`. The completion auto-popup is off in tests. After `type`, a menu is open only when the text matches several items exactly and nothing else. With typed text and exactly one matching item, `Complete` applies it at once with no menu; with nothing typed it always opens the list, even for one item. So assert `isVisible()` only when nothing is typed or two or more items match.
- **Context assistant:** no statement exists; test it in `code` inside `SwingUtilities.invokeAndWait`: `EditorContext editorContext = editor component.getEditorContext();` then, inside `runReadAction`, `ContextAssistantManager m = editorContext.getContextAssistantManager(); m.updateImmediately(); Assert.assertNotNull(m.getActiveAssistant());`, read `((ActionItem) it).getLabelText("")` over `m.getActiveMenuItems()`; after that read action (not inside it), still in the `invokeAndWait`, run the chosen item's `execute("")` in `editorContext.getRepository().getModelAccess().executeCommand(…)`. Querying the menu provider directly passes even when the editor has no context-assistant cell, which shows nothing to a user. Corpus: `testbench/testsolutions/editor.menus.contextAssistant.tests` (MPS sources).
- **Typing alone may already apply an item.** A typed text that equals exactly one item's text, with no other item still prefix-matching it, applies that item without the menu. So a side-transform test is just `type "<exact text>"`, while after a prefix no menu is open in a test: add `invoke action -> Complete` (a sole match is applied at once), then `press ENTER` if two or more items still match. The full rule is in `references/side-transforms.md` in the `mps-aspect-editor-menus-and-keymaps` skill root after loading that companion skill from the same origin. For the same reason a "type, then Complete" test passes even if completion is broken. Assert the menu in between (how to insert `editor component` into parsed Java: `references/editor-test-case/editor-expressions.md`), or check that the test fails without the `Complete` step. Likewise on a non-editable cell (e.g. an empty-line constant): at its edge, each typed character is matched alone as the cell text plus that character (`EditorCell_Label.processKeyTyped` → `IntelligentInputUtil.processCell`). So a one-character item such as a `#` alias applies there through the cell's existing completion, even before your change, while a longer keyword never accumulates. A test that types such a character can pass before the change; check that it fails first.
