| D43 | tool descriptions / `mps-mcp-workflow` reference formats | Module and model parameters use six conventions across sibling tools — `conceptRef`, `conceptRefs`, `languageRefs`, `enumerationRef`, `modelReference`, `moduleName` — and `create_model`'s `moduleName` in fact accepts a module *reference*, the exact value the agent tried to pass as `moduleReference`. Five of nine retries in round 8 were this. Tools that validate in-body return a near-miss-aware message and cost one turn; `insert_root_node_from_json` (`modelReference`) and `create_model` (`moduleName`) declare the parameter required in the signature, so the platform answers with a generic "No argument is passed for required parameter 'x'" that never names the argument it dropped — `S2:75` then spent a `ToolSearch` to recover. | `S1-sonnet-1:103,109`; `S2-sonnet-1:68,75-77` (round 8) | open — remedy is **S**, not docs: make the two parameters optional and validate in-body like `get_concept_details`; see `HOTSPOT_REPORT_round8.md` §4 |
| D44 | `mps-aspect-*` `references/*.md` | Every large reference file opens with a `## Contents / when to read what` block, and agents do not use it: they run `grep -n '^## '` to rebuild the same index, then a ranged `Read`. The block costs bytes in each read and saves no turn. 45 of S1's 131 tool calls (34 %) were skill navigation. | `S1-sonnet-1:27-33` (round 8) | open — **D/T**: put line ranges in the Contents block, or hoist each file's section list into the owning `SKILL.md`; see `HOTSPOT_REPORT_round8.md` §3 |
| D45 | `parse_java_and_insert` | `featureKind: STATEMENTS` into a `*Function` `body` role fails because the role expects a `StatementList`; the caller must insert the `StatementList` first and re-target its `statement` role. The error text says so clearly, but the two-step dance is mechanical. | `S2-sonnet-1:53-55` (round 8) | **fixed** (2026-09-23) — **S**: `parse_java_and_insert` now auto-wraps. `insertAsChild` redirects statements into the role's `StatementList` — reusing an existing one and **appending** (a body role always holds one, and overwriting it the way the single-cardinality branch overwrites an occupant would silently discard a method body), creating one only when the role is empty, so `position`/`index` then refer to the position inside the list; `insertAsReplace` wraps into a new `StatementList` and replaces (the one case where multi-node input is accepted there, since the statements collapse into a single node). The gate is structural, not `featureKind`-based, so `EXPRESSION` into `body` is still rejected; every wrap is reported in `warnings`. `wrapAsConsoleCommand`, which already did this for the console path, now shares the helper. **D**: `mps-baselanguage` `parse-java-tips.md` (the wrap, its two modes, the `position` shift) + `critical-rules.md` (blueprints still never wrap) + the tool description. |
| D46 | `mps_mcp_update_module` + `mps-aspect-migrations` / `mps-aspect-accessories` skills | No tool exposed a language's own `version` int (the field that gates `MigrationScript.fromVersion`, distinct from the consumer-side `languageVersions` stamps): `mps_mcp_update_module` supported only RENAME/CHANGE_VIRTUAL_FOLDER/DELETE, no structure-aspect operation covered it, and no read path emitted it — only the consumer stamps under `usedLanguages`, which is what made the worker mistake one for the other. The skill told the worker to hand-edit the `.mpl`, which cannot work (MPS holds the descriptor in memory and rewrites the file). The console-reflection workaround also failed: it does not resolve in the ephemeral `TempModule` (no `MPS.Core` dependency, and the console module is not addressable by `mps_mcp_module_dependency`), and routing it through a real project module compiled clean but then silently no-op'd via `mps_mcp_run_console_command` (`{"executed":true}`, no history entry, version stays 0). Only the task's own "stop and explain if blocked" instruction ended the retry loop (5 `run_console_command`/`get_console_history` round trips, 3 `sleep` polls, 18 skill-doc greps); first-ever S4 measurement (round 9), task **FAILED** on this alone. **Corrections found while fixing** — (a) the API is trivial (`Language.getLanguageVersion()`/`setLanguageVersion(int)`, `core/kernel/source/jetbrains/mps/smodel/Language.java:278,282`), so the gap was purely surface-level; (b) there is no "New Migration Script wizard" — the bump comes from a lightweight-DSL node factory (`Migration_Queries.init`) that fires only on the `create_root_node` path, see D47; (c) the `FixLanguageVersion` quick fix is **dead code** — `MigrationsCheckUtil.checkMigrationsVersions` reports through `reportTypeError(..., null)` with no intention provider, so nothing references the quick-fix node and `check_root_node_problems(autoApplyQuickFixes=true)` can never repair a version mismatch; (d) the version is **also baked into the generated `LanguageRuntime`** (`MigrationScriptCollector.fillFor` reads `lr.getVersion()`), so a descriptor-only bump satisfies the checker but the migration is still never offered until the language module is rebuilt — a second silent-mismatch trap. | `S4-sonnet-1:29-35` (skill search), `S4-sonnet-1:96-127` (console attempts + stop); `HOTSPOT_REPORT_round9.md` | **fixed** (2026-09-23) — **S**: `SET_VERSION` operation on `mps_mcp_update_module` (omit `newName` to bump by 1; lowering allowed with a warning, mirroring `CorrectLanguageVersion_Action`; consumer stamps deliberately untouched; response carries `languageVersion` / `previousLanguageVersion` / `changed` / `runtimeLanguageVersion` / `runtimeStale` / `runtimeRecoveryAction`, and does **not** run make). Read path: `languageVersion` added to the module-info envelope and emitted on every Language module by `mps_mcp_get_project_structure` without `includeDependencies`. **D**: `mps-aspect-migrations` SKILL + `form-selection.md` + `json-blueprints.md` and `mps-aspect-accessories` SKILL + `module-info-fields.md` + `pitfalls.md` rewritten to name the tool, separate the two version numbers, state the make requirement, and record that the quick fix is unreachable. |
| D47 | `mps_mcp_insert_root_node_from_json` (`AbstractNodeOps.kt:172-173`) | **Node factories are run without a target model on the JSON-blueprint insert path, and whatever they build is then deleted.** `mps_mcp_create_root_node` uses `SNodeFactoryOperations.createNewRootNode(model, concept, null)` (`JetBrainsMPSRootNodeMcpToolset.kt:433`), so `NodeFactoryManager.setupNode` — which walks super-concepts *and* implemented interfaces — invokes each `NodeFactory.setup(node, sample, enclosing, index, model)` with a real `model`. `insert_root_node_from_json` instead calls the 2-arg `SNodeFactoryOperations.createNewNode(sConcept, null)` overload, which forwards `model = null` and `enclosingNode = null`, and the very next line (`AbstractNodeOps.kt:173`) deletes every child the factory produced. For `MigrationScript` (an `AutoInitDSLClass`) the factory is `Migration_Queries.init`, which would set `fromVersion` to the language's current version and bump the language version; with `model = null` it NPEs on `futureModel.getModule()`, the NPE is swallowed by the DSL descriptor's `catch (Exception e) { e.printStackTrace(); }`, and the caller sees an ordinary success envelope with no `fromVersion` and no bump. This is almost certainly the mechanism behind the S4 failure recorded in D46, since `mps-aspect-migrations` routes agents to `references/json-blueprints.md` → `insert_root_node_from_json`. Affects every `AutoInitDSLClass` / factory-initialised concept, not just migrations. | found while fixing D46 (2026-09-23); `AbstractNodeOps.kt:172-173`, `SNodeFactoryOperations.java:49-53`, `NodeFactoryManager.java:131-146`, `DSLDescriptor__BehaviorDescriptor.java:47-65`, `Migration_Queries.java:27-40` | open — **S**: pass the target model to `createNewNode` (or route the blueprint path through `NodeFactoryManager.setupNode`) so factories fire, and stop swallowing factory exceptions; **D** (landed with D46): `json-blueprints.md` now warns that the factory does not run and that `fromVersion` + the version bump must be done explicitly. |

| D48 | no `mps_mcp_*` tool to execute a pending migration; `mps_mcp_reload_all` | With D46 fixed, S4 gets past the version bump cleanly (`languageVersion` read/write both verified working) but still fails end-to-end: there is no MCP tool that runs a pending `MigrationScript` against a consumer model headlessly. The worker's only lever was `mps_mcp_reload_all`, which — because the consumer module's `usedLanguages` stamp (0) now trails the bumped `languageVersion` (1) — makes MPS itself pop its own migration-assistant `DialogWrapper` (`jetbrains.mps.ide.migration.MigrationTrigger.runMigration`, confirmed via `jstack`: `AWT-EventQueue-0` blocked in `Dialog.show`). Every later `mps_mcp_*` call then times out `MODAL_BLOCKED` for the rest of the run. The worker correctly stopped and asked for help rather than forcing anything, but its transcript ended there — task-level result 2/4 criteria (structure + version bump pass; migration-applied + zero-errors fail) even though the fix under test worked. | `S4-sonnet-1` (round 9 re-run, 2026-09-23): server calls 52-56 all `MODAL_BLOCKED`; thread dump `/tmp/mps-threaddump-s4.txt:188-237` | open — **S**: either a headless "run pending migrations on module X" tool (apply without the confirmation UI, mirroring what `MigrationTrigger` does programmatically), or have `reload_all` (or a new explicit trigger) surface `MODAL_BLOCKED`-avoidance by running migrations non-interactively when invoked over MCP. **D**: `mps-aspect-migrations` should say plainly that no tool runs a migration yet and that touching `reload_all` (or anything that re-checks consumer versions) on a version-bumped-but-unmigrated project risks this modal |
